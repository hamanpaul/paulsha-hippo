- 修 issue #89：`FIXED_MAX_AGENT_CALLS=6` 未隨 #85 的 chain 時間預算縮放，導致 7+ chunk session 即使時間充足也必在第 7 次呼叫撞牆而 park。生產實證（2026-07-31T02:00Z）：大 session `claude-code:916106a1` 因 tier-1（`claude`/`codex`）宣告 `max_session_chunks: 6` 判 `ineligible: session_size`，落到 tier-2 `cg` 大 payload 品質不穩（exit 3，10.9KB 輸出、無可解析 JSON），再落到 `local-vllm`（exit 4，在 `max_tokens` 處截斷），三 profile 全滅直接 park，並重置 AR-11 soak 窗口。
- 新增 `agent_profiles.py::effective_max_agent_calls(chunk_count)`，比照 `session_deadline_seconds` 的 floor/cap 造型：`min(max(FIXED_MAX_AGENT_CALLS, chunk_count + 2), FIXED_MAX_AGENT_CALLS_CAP)`。`FIXED_MAX_AGENT_CALLS=6` 不動（≤4 chunk 行為完全不變，`4+2=6`）；新增 `FIXED_MAX_AGENT_CALLS_CAP=20`——`+2` 對齊 #86 chunk 保留契約（一次 fallback 轉移只需重補未驗證的 chunk，2 次呼叫餘裕即夠一次轉移的浪費呼叫）；cap 的防禦目的是擋 runaway 重試而非搶在 1800s 時間預算之前擋住線性進度，`chunk_count+2` 本身已是線性上界，故 cap 需高於時間預算能觸及的最大 chunk 數（1800s ÷ 240s/chunk ≈ 7.5）——20 涵蓋到 18 chunk＋一次 fallback 餘裕，超過屬病理型 split，撞牆屬合理防禦並留下 budget park 證據。
- Review 修正：原定 cap `12` 造成新的「數學上必 park」斷崖——`chunk_count+2 > 12` 在 `chunk_count>=11` 即恆成立，等於任何 ≥13-chunk session 零失敗也必撞牆，剛好摧毀本次修復要解的那批大 session，故 cap 改為 `20`。
- 縮放發生在 `run_session` 內（知道 `chunk_count` 之後），與 `session_deadline_seconds` 造型一致，但語意刻意不同：只有當 router 以**未經修改的預設值**（`self.max_agent_calls == FIXED_MAX_AGENT_CALLS`）建構時才套用縮放；呼叫端明確傳入的其他值（如 operator 收斂過的部署上限、或測試模擬的小型共享預算）維持字面值當硬上限、不縮放。這與 `deadline_seconds`（`run_session`完全不讀 `self.deadline_seconds`，任何非預設設定值即被 config 判 fail-closed）不同——一個明確傳入且異於預設的 `max_agent_calls` 仍會被真實套用（每次呼叫都受它約束），不是「宣告卻被靜默忽略」的同型缺陷，故不需要、也不應該讓 config 對它比照 `deadline_seconds` 做 fail-closed；`atomizer/config.py` 補上對應說明註解記錄兩者為何分岔。跨 profile 累計語意（issue #86 的 retention/shared-budget 契約）完全不變。

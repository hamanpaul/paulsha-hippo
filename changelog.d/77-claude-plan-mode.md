### Fixed
- tier-1 主力蒸餾 backend（`claude` profile）的 argv 移除 `--permission-mode plan`：plan mode 是「探索 → 設計 → 寫 plan → ExitPlanMode 請示」的核可工作流，與 hippo 要求的「直接輸出單一 JSON 文件」契約直接衝突，模型收到真實 atomization prompt 會回頭請示而非執行。實測：48 fragments／100,523 bytes 的 parked session（`claude-code:e41dbdd3-…`）跑 atomize 得 563 bytes、exit 0、35.1s，parser 判 `agent output must be one JSON value without surrounding noise`；以真實 prompt 組裝邏輯重現得 606 bytes 逐字散文，**整段不含任何 `{` 或 `[`**——因此不是「JSON 外包散文」，parser 寬容化救不回來。同一 chunk、其餘 argv 完全不變、只移除該旗標：exit 0、244s、22,778 bytes 合法 schema-1 JSON，生產 parser `parse_response()` 驗證通過。該旗標自 `7182c83`（#34/#39）起未曾變動，亦即 tier-1 主蒸餾在真實 payload 下自那時起即失效，而 probe 因 payload 過小恆綠、`hippo doctor` 看不出來。防寫入能力不受影響：真正禁用工具的是 `--tools ""`（claude CLI 2.1.220 `--help`：「Use `""` to disable all tools」），`--safe-mode`／`--disable-slash-commands`／`--strict-mcp-config` 三個防禦旗標一律保留（#77）。

### Security
- `agent_profiles._validate_argv` 新增 permission-mode 守門（空白與 `=` 兩種寫法皆檢查、值大小寫不敏感）：`--permission-mode plan` 因與單一 JSON 回覆契約衝突而拒絕，`--permission-mode bypassPermissions` 則是既有禁令 `--dangerously-skip-permissions` 的旗標值寫法，一併拒絕。此缺陷之所以能潛伏近整個 release cycle，正是因為 argv 層沒有任何不變量攔得住「宣告了與輸出契約矛盾的 permission mode」的 profile；operator 自訂 config 同樣受此規則保護。另新增出貨模板漂移守門，`atomizer.yaml` 的每個 profile argv 必須與 `agent_profiles.default_profiles()` 逐 token 相同——同一條命令存在兩份 repo 內副本，只修其中一份就等於照樣出貨帶病的設定。
